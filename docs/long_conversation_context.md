# 学生助手长会话上下文与评估

## 运行机制

每个已绑定课程的会话用 `session_id` 作为 LangGraph `thread_id`。已有 checkpoint 时，
`agent_runner.py` 只提交本轮用户消息；checkpoint 不存在时才从 Redis、业务 SQLite
恢复近期聊天。业务 SQLite 保存原始问答，Redis 保存近期问答缓存；摘要、近期完整轮次和
工具调用状态属于 LangGraph checkpoint，保存在 `agent_checkpoints.db`。

`StudentConversationSummarizationMiddleware` 仅在新用户问题进入时检查压缩条件：
估算输入达到 4000 token 且状态至少 12 条消息。压缩时，最多保留最近三个以用户消息
开头的完整轮次（包括当前问题），并尽量使保留部分低于 3000 个估算 token。
当前用户问题即使单独超限也保留。旧轮次经摘要模型生成滚动摘要；旧工具结果中的
`course_id`、`topic`、`question_id`、`material_id`、`chunk_id`、来源和检索顺序
被提取为有长度上限的索引。索引优先考虑本轮明确提及的 ID、知识点、题目/资料类型、
时间先后。它是重新查询原文的地址，不是题目或资料原文，也不承诺保存所有历史 ID。

资料索引保留检索顺序 `position`。例如用户说“第二段资料”，Agent 可从同一次检索的
`material_chunks` 中取 `position=2` 的 `chunk_id`，用精确读取工具重新获取正文。
如果存在多次检索，无法确定所指的“第二段”，应澄清；如果索引因容量限制已丢失，
可在当前课程重新检索。精确读取工具用运行时学生和课程范围校验，不能因为摘要中写了
一个课程 ID 就越权读取。

旧工具结果过长时，模型输入中使用索引卡；checkpoint 中仍可保留该次工具结果原文。
会话摘要真正替换的是 checkpoint **当前状态**中的旧消息。历史 checkpoint 版本和业务
SQLite 聊天记录不会因此立即缩小。

## 可复现的离线对照

在项目根目录执行：

```powershell
E:\heima\.venv\Scripts\python.exe -m tests.manual_benchmark_long_context
```

脚本用相同的 25 轮模拟会话分别运行无摘要和有摘要两组。两组都使用旧工具结果索引卡、
临时 SQLite checkpoint，以及固定的课程资料和错题数据；第 13 轮重新创建 Agent，验证
从磁盘恢复。最后追问“第二段资料”和“Q03 为什么做错”，按精确工具重取成功且回答包含
预设事实计为通过。输入 token 使用 LangChain 的 `count_tokens_approximately` 估算；
本地耗时是三次运行的每轮平均值，不包括 DeepSeek 网络和真实模型推理。

2026-10-08 本机结果：

| 指标 | 无摘要 | 有摘要 |
|---|---:|---:|
| 平均主模型输入 token/轮 | 4418.7 | 3094.9 |
| 平均总输入 token/轮（含摘要模型） | 4418.7 | 3241.2 |
| 平均本地耗时/轮 | 6.7 ms | 8.0 ms |
| 指定追问精确重取 | 2/2 | 2/2 |
| 最终 checkpoint 活跃消息数 | 57 | 33 |
| 摘要模型调用数 | 0 | 1 |

总输入减少约 26.6%。这组 2/2 表示**脚本驱动的精确重取链路通过**，不是 DeepSeek
在真实学生提问上的回答正确率。要测真实回答正确率，需要固定题集、判定标准和模型版本，
运行实际模型并逐题核对答案与引用；时间也应单独记录网络与模型耗时。

## DeepSeek 合成会话小样本

运行 `python -m tests.manual_deepseek_long_context`。脚本向 `deepseek-chat` 发送同一段
合成课程历史，分别关闭、开启摘要；两个问题均要求用工具精确重取资料片段或错题。
测试使用临时 checkpoint 与模拟的课程服务，不涉及生产学生记录。输入 Token 读取模型
返回的 `usage_metadata.input_tokens`；耗时包括摘要、主模型、工具调用及网络。
2026-10-08 单次对照结果如下：

| 指标 | 无摘要 | 有摘要 |
|---|---:|---:|
| 两次追问的主模型输入 Token | 49,001 | 21,445 |
| 摘要模型输入 Token | 0 | 10,357 |
| 两次追问的总输入 Token | 49,001 | 31,802 |
| 两次追问的总耗时 | 5.74 秒 | 8.25 秒 |
| 指定证据精确重取且答案包含预设事实 | 2/2 | 2/2 |

计入摘要调用后，输入 Token 减少约 35.1%。压缩组第一次追问用 5.54 秒，其中包含
一次摘要调用；第二次追问用 2.71 秒。样本只有两题，这个 2/2 是合成题的通过率，
不能据此声称真实学生问题的总体正确率。耗时会随网络和服务端负载变化，不能视为
稳定的延迟收益；后续要做正式评估，应扩展题集并重复多次。

## 面试时的解释

**为什么保留这些消息？** 最近完整轮次让“这个是什么意思”“继续”仍有原文可指；
只按消息条数截取可能把一次工具请求和结果分开。三轮是可调整的经验参数，
3000 token 是旧轮次的预算；是否合适应由追问测试和输入成本共同验证。

**压缩丢了“第二段资料”怎么办？** 索引记录片段原始顺序与 ID，Agent 按 `position=2`
找到同一次检索中的片段并重新调用课程范围内的精确读取工具。若索引缺失则重新检索，
若存在多次可能的“第二段”则先澄清，不凭摘要编造正文。

**摘要存在哪里？** 摘要是一条标记为 `lc_source=summarization` 的 LangGraph 消息，
随同该 `thread_id` 的当前状态持久化到 `agent_checkpoints.db`。Redis 用于近期问答缓存，
业务 SQLite 保存原始聊天；已有 checkpoint 时不会再把 Redis 历史注入同一轮。
